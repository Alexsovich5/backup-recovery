# Automated Backup and Recovery System

A small Bacula 5.2 backup and recovery setup for one Linux client, run as a self-contained Docker stack. It has templated Bacula configuration (Director, Storage Daemon, File Daemons, bconsole) backed by a MySQL catalog, with a weekly Full/Differential/Incremental schedule and client-side PKI encryption and signing. Around that it adds Bash tooling that drives `bconsole` non-interactively for backups, restores, verify jobs and restore tests, a Python 2.7 catalog report with Nagios-style exit codes, mail notifications through `bsmtp`, an rsync copy of volumes, bootstrap files and the catalog dump to an offsite host, and a disaster-recovery drill that restores the client's data using only that offsite copy and the master recovery key.

Personal project built on the 2013-era stack (Bacula 5.2.6, MySQL 5.5.35, Bash 4.2, Python 2.7.3, rsync 3.0.9 on Debian wheezy).

## Status

**Implemented**

- Templated Bacula configs rendered from an env file by `scripts/render-config.sh`. The placeholder handling is tested in `tests/unit/render-config.bats`. The rendered SD/FD/bconsole configs are syntax-checked with `-t` in `make lint` and `tests/unit/config-syntax.bats`, and the Director config is checked with `bacula-dir -t` against the live catalog in `tests/integration/10-stack.bats`.
- MySQL catalog created with Bacula's `make_mysql_tables` (`docker/entrypoint-catalog.sh`), with Full, Differential and Incremental pools on separate retention (`config/bacula-dir.conf`). Tested in `tests/integration/10-stack.bats` and `tests/integration/20-backup.bats`.
- Scheduled backups: one `server01-backup` job on the `WeeklyCycle` schedule (Full on the 1st Sunday, Differential on the other Sundays, Incremental Monday to Saturday) plus `BackupCatalog` (`config/bacula-dir.conf`). `tests/integration/10-stack.bats` checks that these two are the only scheduled jobs.
- On-demand backups with `scripts/backup.sh <client> <full|incremental|differential>`. It waits for the job and exits non-zero unless the job ends in status `T`. Shared bconsole helpers live in `scripts/lib/common.sh`. Tested in `tests/unit/backup.bats`, `tests/unit/common.bats` and `tests/integration/20-backup.bats`.
- Client-side PKI encryption and signing, with a per-client keypair and a separate master recovery key generated by `scripts/gen-keys.sh` (`config/bacula-fd.conf`). Tested in `tests/unit/gen-keys.bats` and `tests/integration/30-encryption.bats`, which checks that a plaintext marker appears in an unencrypted control volume but not in the client's volumes, and that a File Daemon without the key cannot decrypt the data (`tests/integration/40-restore.bats`).
- Non-interactive restore CLI `scripts/restore.sh`, which restores the full tree or selected files, from the newest backup or a point in time, optionally to another File Daemon. Tested in `tests/unit/restore.bats` and `tests/integration/40-restore.bats`.
- Verification: a `VolumeToCatalog` verify job queued exactly once per backup, by `scripts/queue-verify.sh` from the scheduled job's RunScript or by `scripts/backup.sh` for on-demand runs. There is also an automated restore test, `scripts/restore-test.sh`, that compares MD5 checksums against a manifest from `scripts/make-manifest.sh`. Tested in `tests/unit/queue-verify.bats`, `tests/unit/restore-test.bats`, `tests/unit/make-manifest.bats` and `tests/integration/50-verify.bats`, including a tampered manifest that must fail.
- Catalog health report `bin/catalog_report.py` (Python 2.7). It reports failed backup and verify jobs and clients without a recent good backup, with exit codes 0/1/2/3. Tested in `tests/python/test_catalog_report.py` and `tests/integration/60-report.bats`.
- Mail notifications from the Bacula `Messages` resources and from `scripts/backup.sh` through `bsmtp`. Tested in `tests/unit/backup.bats` and `tests/integration/70-notify.bats`.
- Offsite copy: `BackupCatalog` dumps and backs up the catalog, then `scripts/offsite-sync.sh` copies volumes, `.bsr` files and the dump to the offsite rsync daemon. Tested in `tests/unit/offsite-sync.bats` and `tests/integration/80-offsite.bats`.
- Disaster-recovery drill `scripts/dr-drill.sh`. It recovers the catalog dump with `bextract`, loads it into a scratch database, starts scratch Director/SD/FD daemons that hold only the master key, restores the client's data and checks it against a manifest. Run with `make dr-drill`. Tested in `tests/unit/dr-drill.bats` and `tests/integration/90-dr-drill.bats`.

**Not implemented / known limitations**

- No tape drives or autochangers. A disk-based File device stands in for tape.
- One Linux client only (`server01`). No other production clients, no Windows clients.
- No graphical recovery interface (bat, Bweb, webmin). Recovery is the `scripts/restore.sh` CLI.
- No TLS between Bacula daemons. PKI encrypts file contents only, so file names, attributes and the control channel are not encrypted.
- No real remote DR site or WAN replication, and no real mail server (see Mocks below).
- No systemd service checks. wheezy uses sysvinit, so the Director is probed with `bconsole status dir`.
- No cron scheduling. Bacula's own scheduler runs the jobs.
- No placeholder `src/`/`docs/`/`tests/` tree from an earlier README draft. The layout below is the real code.
- Business-impact claims from an earlier draft were removed, because nothing in this repo measures them.
- The base image is the final wheezy build (7.11), so libraries already in the base image (libc, bash, coreutils) are newer than the pinned packages. Everything apt installs comes from the 2014-01-31 snapshot.debian.org suites.
- Apt installs use `--force-yes` because the wheezy archive signing keys have expired. Package authenticity rests on snapshot.debian.org.
- Scheduled runs (23:05, 23:30) are configured and listed, but the tests do not wait for the wall clock. They trigger the same jobs explicitly.
- Building the image needs snapshot.debian.org to be reachable.
- The image is amd64-only. On ARM hosts it runs under emulation and is slow.

**Mocks and simulated parts**

- Offsite site = `offsite` container running an rsync daemon (`config/rsyncd.conf`, `docker/entrypoint-offsite.sh`).
- DR recovery host = scratch `drill-dir`/`drill-sd`/`drill-fd` daemons that `scripts/dr-drill.sh` starts inside the director container (configs in `config/drill/`).
- Master-key safe = the `keys` volume, mounted read-only into the director at `/keys`.
- Mail = Python 2.7 `smtpd.DebuggingServer` sink in the `smtp` container (`docker/entrypoint-smtp.sh`).
- Tape = disk File device (`config/bacula-sd.conf`).
- Production server = the `server01` container running `bacula-fd` over fixture data from `tests/fixtures/data/`.
- `bconsole` and other binaries (`rsync`, `bsmtp`, `bextract`, `mysql`, the Bacula daemons) = stubs in `tests/unit/stubs/` for the unit tests, replaying fixtures from `tests/fixtures/bconsole/`.
- MySQL = `mock` connection and cursor in the Python unit tests (`tests/python/test_catalog_report.py`).

## Running it

Everything runs in Docker images from the project's era, so nothing needs installing locally beyond Docker.

```bash
make image env           # build backup-recovery:wheezy and create config/bacula.env from the example
docker compose up -d     # start catalog, director, server01, smtp and offsite
docker compose exec director /src/scripts/backup.sh server01 full
```

Other entry points inside the director container are `/src/scripts/restore.sh --client server01` and `/src/bin/catalog_report.py --host catalog --password-file FILE` (FILE holds `DB_PASSWORD` from `config/bacula.env.example`). From the host, `make dr-drill` runs the disaster-recovery drill against the running stack.

## Tests

```bash
make test                # lint + unit + integration, all inside the period image
```

`make lint` syntax-checks every script and the rendered SD/FD/bconsole configs. `make unit` runs the Bats suites in `tests/unit/` against stubbed binaries and the nose suite in `tests/python/` against a mocked database. `make integration` brings the whole stack up and runs `tests/integration/` inside the director, covering real backups, encryption, restores, verify jobs, the report, mail, the offsite copy and the DR drill. The tests do not cover real hardware, real remote hosts or waiting for the wall-clock schedule.
